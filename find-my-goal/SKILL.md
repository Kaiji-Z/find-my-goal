# find-my-goal：零门槛写强目标

用户的心智模型一句话：**说带"目标"的愿望 → 答几道选择题 → 把产出的目标交给 /goal 跑。**

/goal 本身是 agent 内核的循环机制（持久状态、自动续跑、完成校验），那些不用你操心，也不要去检测它存不存在。**你只负责一件事**：把"帮我优化项目"这类模糊愿望，翻译成一段可验证、有刹车的强目标。写好 prompt 的知识在你这里，不在用户那里。

## DRAFT 流程：模糊愿望 → 强目标

### 0. 先收割已有讨论

用户说"按刚才讨论的设个目标""把这个方向变成 goal"时，最富的信息源是这场对话，不是追问：

- **提取**：商定的方向、涉及的文件/模块、已说过的约束、讨论中已跑过的数字（讨论时跑过测试/benchmark 就直接用作 baseline，不要重跑）。
- **对照交付格式查缺**：目标 / 范围 / 判据 / 停止条件 / 预算——只问真正缺的。带着上下文来时通常只剩判据细节和预算，一到两道选择题就够；判据缺失时基于讨论内容直接提一个让用户确认，你见过上下文，问得就该比冷启动少。
- **关键决定写进目标文本**：讨论中的方案取舍、已知坑、用户明确的偏好，要么写进目标本身，细节多时写入 `.goal/SPEC.md` 并让目标指向它——目标执行会跨上下文压缩甚至换会话，目标文本必须自包含，不能指望它记得这场讨论。

### 1. 模糊词检测

愿望里出现"优化 / 提升 / improve / optimize / 清理 / clean up / 重构一下 / 完善 / 更好 / 增强"这类没有可验证终点的词时，**不要直接出稿**——这句话是愿望，不是规格，进入追问。（若愿望本身已含可验证终点，如"把 47 个 failing 测试修到全绿"，跳过追问直接出稿确认。）

### 2. 选择题式追问（最多 3 轮）

规则：一轮只问一个问题；每个问题给 2-3 个选项；选项里永远有一个"你帮我定"；用户嫌烦或答不上来，全部按"你帮我定"处理，直接出稿。绝不做开放式提问——用户答不出"验证面是什么"这种问题。

照抄这三个模板：

> **Q1 验收**：「{原话}」做到什么程度算完成？
> A. 我先看看项目现状，提一个能验证的标准给你确认
> B. 我直接告诉你（自由输入）
> C. 说不清，你定个保守的

> **Q2 边界**：过程中只允许动哪些东西？
> A. 相关文件随便动，但别碰测试之外的公开接口 / 别装新依赖（默认）
> B. 只许改我指定的文件
> C. 你判断

> **Q3 预算**：最多试多少轮？
> A. 15 轮（默认）
> B. 你按任务规模定
> C. 我说个数

### 3. 你帮用户定时（用户选 A/C 或没答）

去看项目：读相关代码和配置，能跑就跑一次 baseline（测试、构建、benchmark）。把模糊词翻译成**带数字的判据**：具体命令 + 期望退出码或输出阈值。拿不准就选更容易验证、更保守的判据。

例："帮我优化项目" + 全套"你帮我定" → "把 `npm test` 全量耗时从 baseline 84s 压到 40s 以内，且全部通过"。

### 4. 出稿确认

按交付格式生成完整目标，原文展示给用户，明确说"**确认后交给你的 /goal 执行**"。用户要改就改，改完再确认。**未经确认不定稿。**

## 交付格式

各家循环命令（原生 /goal、omo 的 /goal、/ralphloop……）吃的都是一段目标文本，这份格式通用：

```
目标：{一句话结果，含数字}
范围：只许 {范围}；禁碰 {禁区}
完成判据：{命令 + 期望退出码/输出阈值}（可多条，逐条可验证）
停止条件：{需要用户决策的事；同一思路连续 3 次失败}
预算：最多 {N} 轮迭代
```

细节过多时（或目标给 Codex，其限 ≤4000 字符）：把细节写入项目文件（如 `.goal/SPEC.md`），目标文本里写"先读 .goal/SPEC.md 并确认后执行"。

## 硬规则

- **判据的野心决定轮数**：一轮就能全部达标的判据，goal 一轮（正确地）就结束——这不是故障。若任务本质是迭代实验（性能调优、flaky 排查、方案探索），做两件事：判据定在「单次尝试难以一次达到」的水平（如 baseline 84s → 40s，而非 84s → 75s）；并在目标里写明迭代结构，如「每轮只验证一种思路，测量并记录结果后再进入下一轮，单轮内不得同时实施多种变更」。同时加防作弊条款：不得修改测试、基准或判据本身来达成判据。
- 完成判据必须**可执行、可复核**：具体命令 + 期望退出码/输出阈值。"全部变好""代码更干净"不是判据。
- 预算和停止条件必填。没有刹车的长跑目标会烧掉用户的钱——这是特性不是仪式。
- 范围必填。明确禁区（不许碰的文件/依赖/公开接口）。
- 用户没确认不定稿；用户改口径以用户为准。

## 特殊情况

- 用户在消息文本里输入了 "/goal ..."（agent 没有原生 /goal 命令时才会这样），或明说"我没有 /goal"：不检测、不建议换工具，问一句"要我把这份目标在当前会话里直接执行吗？我按判据逐条验证推进"。用户说行，就照目标文本执行：每轮改动 → 重跑判据命令取证 → 全部达标才收工，命中停止条件就停下问。
- 用户拿出一段已写好的 goal 让你"看看强不强"，或抱怨"我的 goal 在空转/跑偏了"：空转几乎总是弱目标所致（无判据、无预算）。按硬规则逐条体检重写，改动处标明；若该 goal 已在执行，提醒用户清掉旧目标（`/goal clear` 或对应命令）、用新文本重新设置。
- 用户直接打 `/goal 弱目标`（在**有**原生命令的客户端，这条输入会被内核截获直接执行，本 skill 看不到、拦不住）：凡有机会与用户对话，主动传达口诀"**先写后跑**"——先说'帮我写个 goal'拿到成品，再 /goal 粘贴执行。
